# KONG 验收与测试计划

版本：0.2  
适用阶段：LAN MVP（P0）及封测质量（P1）  
关联：[KONG 开发文档](KONG_开发文档.md)、[网络协议 V1](网络协议_V1.md)

## 1. 测试原则

- 每个规则决定、每条 RPC 和每项异常行为必须至少有一个可执行测试。
- 测试结果只能是 `通过`、`失败`、`阻塞`、`未执行`；口头“应该可以”不算通过。
- 发现问题先记录复现步骤、构建版本和预期/实际结果，再做最小修复；禁止借测试机会重写状态机。
- 测试环境、构建版本、日期、执行者和结果必须可追溯。

## 4. 必测案例

主规格的 T01–T20 是功能核心。本表补充当前版本必须覆盖的边界与网络测试。

| ID | 环境 | 前置条件与步骤 | 通过条件 |
| --- | --- | --- | --- |
| P0-R03 | E1 | 构造两个或多个最高者完全同分；再构造全员完全同分 | 前者全部最高者扣血，后者无人扣血 |
| P0-R04 | E1 | 玩家成功贴掉最后一张牌，轮到该玩家 | 可喊 Kongbaya；从抽牌堆取到普通牌可弃；不能取弃牌顶或替换 |
| P0-R05 | E1 | 0 张手牌玩家获得可使用的 7–Q | 能按能力流程完成，状态不死锁 |
| P0-R06 | E1 | 令抽牌堆为空且弃牌堆仅余顶牌 | 有手牌者可取弃牌顶；无手牌者触发立即结算；不出现无限等待 |
| P0-N01 | E1 | 非当前玩家依次发送取牌、替换、技能、Kongbaya 请求 | 全部拒绝，其他玩家状态和牌数不变 |
| P0-N02 | E1 | 为请求传入负数、越界、他人槽位 | 收到 `INVALID_SLOT` / `INVALID_TARGET`，无状态变化 |
| P0-N03 | E1 | 从弃牌堆取到 7–Q 后发送使用能力 | 收到 `ABILITY_FORBIDDEN`，仍只能替换 |
| P0-N04 | E1 | 同一动作 ID 连续提交两次 | 仅执行一次，第二次为幂等返回或重复拒绝 |
| P0-N05 | E1 | 向服务器发送未知/旧 `match_id` | 拒绝，不影响当前对局 |
| P0-N06 | E1 | 当前玩家停在抽牌或 Q 决策至少 35 秒 | 对局不自动跳过；贴牌窗口仍按服务器时间关闭 |
| P0-N07 | E2/E3 | 两人同时/连续猜错同一窗口 | 各自最多罚一次；窗口仍可被第三人/另一正确玩家结束 |
| P0-N08 | E2 | 非房主在 `TURN_DECISION`、`SLAP_WINDOW`、`Q_DECISION` 各断线一次 | 房主与剩余玩家看到中止；无结算、无扣血 |
| P0-N09 | E2 | 房主中途退出 | 客户端显示房主断开并清空本局 |
| P0-S01 | E1 | 导出普通 `match_snapshot`、事件日志与 UI 内存显示，检查所有未公开牌 | 无 `rank/suit/value/label`；仅私有查看和结算含牌面 |
| P0-S02 | E3 | 四人完成包含 J、Q、贴牌和 Kongbaya 的完整局 | 无客户端状态不同步、无重复结算、无卡死 |

## 5. P0 发布闸门：LAN 可玩 MVP

只有同时满足以下所有条件，才可标记为“LAN 可玩 MVP”：

1. T01–T20 和本文件所有 `P0-*` 测试均为“通过”，不存在“阻塞”或“未执行”。
2. E1 连续完成 **20 局**两人对局；E2 连续完成 **10 局**两人对局；E3 完成 **5 局**四人对局。期间无崩溃、死锁、重复抽牌/换牌、不同结算结果或暗牌泄露。
3. 每局至少覆盖一次：普通替换、从弃牌堆替换、一次技能、一次贴牌窗口和 Kongbaya。整套样本累计覆盖 7/8、9/10、J、Q 的两个分支。
4. 在 E2/E3 的局域网下，至少 95% 的普通操作由所有参与者在 **200 ms** 内看到新状态；贴牌发生时由服务器的第一个有效请求稳定获胜。
5. 断线测试按 P0-N08/P0-N09 完成，且中止不会造成生命变化或假结算。
6. 所有失败项有 issue/记录，且无 `阻断对局`、`规则错误` 或 `信息泄露` 未关闭。

不满足任何一项时，只能称为“原型”或“验证中”，不能对外称为 LAN MVP。

## 6. P1 封测闸门

在 P0 之上，封测前还必须：

- [ ] V1 协议的版本、revision、幂等和拒绝码完整实现并通过第 7 节验收；
- [ ] 有房间创建/加入/中止的结构化服务器日志；
- [ ] E4 人为网络扰动下，无崩溃、无违反服务器顺序的贴牌结果；
- [ ] UI 对每个拒绝码有可理解提示，且不显示过期操作为成功；
- [ ] 已完成基础无障碍检查：文字可读、按钮可点击、色彩不是唯一状态提示；
- [ ] 封测问卷显示大多数玩家无需讲解也能完成一次抽牌、替换和贴牌尝试。

### E1 自动化双实例验证（verify_net）

`tests/verify_net.tscn` 提供 headless 自动化验证：host 实例建房，client 实例以 `127.0.0.1:7007` 加入，自动走完注册、开局确认、抽牌、替换、贴牌窗口超时、轮换，双方各完成 4 次 `TURN_DRAW` 后判定 PASS 退出。

运行方式（先 host 后 client）：

```bash
godot --headless --path . res://tests/verify_net.tscn -- -role host
godot --headless --path . res://tests/verify_net.tscn -- -role client
```

## 8. 缺陷分级与处理

| 等级 | 定义 | 发布影响 |
| --- | --- | --- |
| Blocker | 无法建房/加入/完成一局；崩溃；死锁 | 阻断 P0 |
| Critical | 规则错误、暗牌泄露、错误结算、客户端可改变他人状态 | 阻断 P0 |
| Major | 重要流程反馈错误、断线后错误状态、严重视觉误导 | P0 前应修复；例外需书面批准 |
| Minor | 拼写、无影响的布局和动画瑕疵 | 可进入 P1 排期 |

## 9. P2 Roguelike 数据判定

单局遗物进入封测后，记录：选择率、持有者胜率、平均回合数、贴牌成功率、喊 Kongbaya 的回合数、玩家主观“是否必选”。连续 20 局样本中，某遗物若选择率或胜率明显压制其他内容，先停用或削弱，不以“增加更多强遗物”解决。
