# KONG 网络协议 V1

> **本文档职责**：客户端/服务器**协议契约权威**（RPC/快照字段、错误码、隐私、幂等）。开发实现见 `功能实现文档.md`；规则见 `KONG_开发文档.md`。改动协议字段前必须先更新本文档。

状态：**MVP 目标契约，待原型验证后逐项对齐**  
传输：Godot High-Level Multiplayer / ENet / UDP，可靠有序 RPC  
权威：房主服务器（LAN）或 Headless 服务器（VPS）  
关联主规格：[KONG 开发文档](KONG_开发文档.md)

本文定义客户端与规则服务器之间的接口，而非 UI 内部事件。任何新增 RPC、字段或规则必须先更新本文并提升 `protocol_version`（不兼容）或文档修订号（兼容）。

## 1. 协议状态与兼容规则

| 项目 | V1 要求 | 当前原型状态 |
| --- | --- | --- |
| `protocol_version` | 固定整数 `1`，加入大厅前双方必须相等 | 已实现：注册 RPC 携带版本，不匹配返回 `PROTOCOL_VERSION_MISMATCH` |
| `match_id` | 服务器建局时生成的不透明随机字符串 | 已实现：`_server_start_match` 生成并写入快照 |
| `state_revision` | 每次状态改变递增，客户端只接受更大的值 | 已实现：每次广播递增；客户端丢弃 `<=` 旧包 |
| `client_action_id` | 客户端每次命令生成 UUID；服务器按玩家去重 | 已实现：全部命令携带，每玩家保留最近 64 个，重复返回 `DUPLICATE_OR_EXPIRED_ACTION` |
| RPC 顺序 | 可靠、有序；服务器仍要按状态验证，不信任到达顺序 | 已采用 |

在 V1 完整对齐前，所有 LAN 客户端必须来自同一项目构建版本。版本不匹配时服务器返回 `PROTOCOL_VERSION_MISMATCH`，客户端不得进入大厅。

## 2. 通用类型与约束

| 类型 | 格式 / 范围 | 说明 |
| --- | --- | --- |
| `PeerId` | 正整数 | ENet peer ID；LAN 房主服务器本地 ID 为 `1` |
| `SeatId` | 0 起始整数 | **玩家身份**（0..N-1，注册顺序分配）；`players`/`turn_order`/`current_player`/`viewer_id`/动画事件中的玩家字段一律用 `SeatId`。`PeerId` 仅是当前连接，掉线重连会变化，`SeatId` 跨连接稳定（VPS 场景同样适用） |
| `Slot` | 0 起始整数 | 玩家当前手牌数组中的位置；不得缓存为永久坐标 |
| `CardId` | 不透明随机字符串 | 只用于 UI 追踪位置；不能编码点数、花色或牌堆顺序 |
| `Rank` | `A`、`2`–`10`、`J`、`Q`、`K`、`JOKER` | 仅在公开/私有允许时发送 |
| `CardView` | `{id, rank, suit, value, label}` | 牌面可见时使用 |
| `HiddenSlot` | `{card_id}` | 牌面未知时使用；不得有 `rank/suit/value` |
| `Phase` | `LOBBY`、`INITIAL_PEEK`、`TURN_DRAW`、`TURN_DECISION`、`Q_DECISION`、`SLAP_WINDOW`、`SLAP_EXCHANGE`、`GAME_OVER`、`SLAP_DUEL`、`BET`、`SHOP` | 枚举名称是契约；数字仅为当前实现细节（`BET`=9、`SHOP`=10） |

所有昵称必须去除首尾空白、限制为 1–16 个可见字符。客户端输入仅用于显示；服务器可进一步过滤不安全字符。

## 3. 请求方向：客户端 → 权威服务器

在 Godot 中，以下行为可以表现为对应的 `server_*` RPC。每一项逻辑请求都应包含或由传输关联 `protocol_version`、`match_id`、`client_action_id`；表中只列业务载荷。

| 业务请求 | 业务载荷 | 合法阶段 | 服务端必须验证 |
| --- | --- | --- | --- |
| `register_player` | `{display_name}` | `LOBBY` | 协议版本、未注册、未满员；注册后服务器定向返回 `player_token` |
| `reconnect` | `{player_token, display_name}` | 任意（对局进行中） | token 有效、目标座位存在且离线、协议版本 |
| `start_match` | `{ match_limit: Integer }` | `LOBBY` | 调用者为房主、2–4 人；`match_limit` 为系列赛局数（2-10，越界回退默认 5；客户端可不传） |
| `initial_ready` | `{}` | `INITIAL_PEEK` | 调用者在本局且尚未确认 |
| `bet` | `{ amount: Integer }` | `BET` | 存活玩家、尚未押注；`amount==0` 表示 all-in（仅货币 < 入场时合法，押全部货币 + 灵魂币）；否则 `20 ≤ amount ≤ 100`、`(amount-20) % 5 == 0`、`amount ≤ 当前货币` |
| `take` | `{source: "draw" | "discard"}` | `TURN_DRAW` | 调用者为当前玩家、来源可用；0 张手牌不得取弃牌顶 |
| `replace` | `{slot}` | `TURN_DECISION` | 当前玩家、槽位属于调用者、存在待处理牌 |
| `discard_draw` | `{}` | `TURN_DECISION` | 当前玩家、待处理牌来源为抽牌堆 |
| `use_ability` | 见下表 | `TURN_DECISION` | 当前玩家、待处理牌来自抽牌堆、牌面具有对应能力 |
| `q_decision` | `{exchange: bool, own_slot?: Slot}` | `Q_DECISION` | 当前玩家即 Q 操作者；换牌时 `own_slot` 合法 |
| `slap` | `{target_player: PeerId, slot: Slot}` | `TURN_DRAW`（且 `slap_open`） | 目标槽位存在 |
| `slap_duel_stop` | `{}` | `SLAP_DUEL` | 调用者为比拼候选人、未按过 STOP |
| `slap_exchange` | `{own_slot: Slot}` | `SLAP_EXCHANGE` | 调用者即贴中他人者、自己的槽位存在 |
| `kongbaya` | `{}` | `TURN_DRAW` | 调用者为当前玩家 |
| `next_match` | `{}` | `GAME_OVER` | 调用者为房主（seat0）、人数 ≥ `MIN_PLAYERS`；成功后 `match_number += 1`、全员重发 `HAND_SIZE` 张、回 `INITIAL_PEEK`，快照 `result` 清空。**注**：把末（`_series_finished`）后调用被拒；非把末由服务器 Timer 自动触发，客户端无需手动调用 |
| `shop_buy` | `{offer: Integer, action_id}` | `SHOP` | 存活玩家、尚未完成（限购 1 件）；`offer` 为货架索引；该件未售出（越界/已售出 → `INVALID_OFFER`）；货币 ≥ 该件固定价（不足 → `INVALID_AMOUNT`）；成功后扣款、遗物入库并广播 |
| `shop_skip` | `{action_id}` | `SHOP` | 存活玩家、尚未完成；跳过购买（不买，视为完成）；全员完成（购买或跳过）→ 开下一局 |
| `joker_transform` | `{rank: String, suit: String, action_id}` | `TURN_DECISION` | 调用者为当前行动者、持有 Joker 变换遗物、`pending_draw` 牌面为 `JOKER`；`rank` ∈ A..K、`suit` ∈ ♠♥♣♦；成功后服务器把 pending 卡改 `rank/suit/value` 并广播（非 JOKER / 无遗物 → `ABILITY_FORBIDDEN`） |

`use_ability` 的载荷：

| 抽到的牌 | 载荷 | 附加验证 |
| --- | --- | --- |
| 7 / 8 | `{slot}` | `slot` 属于调用者 |
| 9 / 10 | `{target, target_slot}` | `target != 调用者`，目标槽位存在 |
| J | `{target, own_slot, target_slot}` | `target != 调用者`，双方槽位存在 |
| Q | `{target, target_slot}` | `target != 调用者`，目标槽位存在 |

服务器不得接受客户端提交 `CardId`、`Rank`、分值、洗牌结果、结算结果或计时结果作为规则依据。

## 4. 响应方向：权威服务器 → 客户端

### 4.1 大厅快照 `lobby_snapshot`

```text
{
  protocol_version: 1,
  lobby_revision: Integer,
  host_id: PeerId,
  min_players: 2,
  max_players: 4,
  players: [{ id: PeerId, name: String }]
}
```

此消息不能包含发牌随机种子、卡牌、匹配历史或任一玩家 IP。

### 4.2 对局快照 `match_snapshot`

每次权威状态发生可见变化时，服务器向每位已连接玩家发送一份独立快照。

```text
{
  protocol_version: 1,
  match_id: String,
  state_revision: Integer,
  phase: Phase,
  current_player: SeatId | null,
  current_name: String,
  viewer_id: SeatId,
  draw_count: Integer,
  discard: CardView | {},
  players: [{
    id: SeatId,
    name: String,
    count: Integer,
    health: Integer,
    currency: Integer,
    eliminated: Boolean,
    slots: HiddenSlot[] | ({card_id, card: CardView})[]
  }],
  pending?: CardView,
  slap_rank: Rank,
  slap_open: Boolean,
  slap_duel?: { contestants: SeatId[], duration_ms: Integer, deadline_server_ms: Integer, target: Number },
  slap_exchange_actor?: SeatId,
  suspended: Boolean,
  offline_players: SeatId[],
  kong_caller?: SeatId,
  bet_ready: SeatId[],
  match_number: Integer,
  run?: { match_limit: Integer, relics: { relic_id: {...} } },
  shop?: { offers: [{id, name, min_bid, bidders}], submitted: SeatId[] },
  shop_result?: { offer_index: {relic_id, name, winner: SeatId, amount} },
  event_log: String[],
  result?: MatchResult
}
```

`player.id`/`current_player`/`viewer_id`/`slap_duel.contestants`/`slap_exchange_actor`/`kong_caller` 一律为 `SeatId`；客户端只比较这些字段是否相等（如 `player.id == viewer_id`），不依赖其绝对值对应网络 peer。

`suspended`：条件暂停标志（当前行动者离线 / 开局记忆或押注阶段任一存活玩家离线）。`offline_players`：当前离线座位列表。二者为公开信息，客户端据此显示"对局暂停"与房主操作按钮（踢出/中止）。

`bet_ready`：仅 `BET` 阶段存在，为已押注存活玩家的 `SeatId` 列表（客户端据此显示"已押注"状态）；非 `BET` 阶段为空数组。`players[].currency`：玩家当前货币（押注时已扣，用于押注面板与玩家区域显示）。`result.economy`：仅结算存在，形如 `{ seat: Integer净变化 }`（正=赚、负=失），客户端据此在结算页显示"本局货币变化"；`result.penalized`：本局 all-in 且垫底（含超限 R-07、首回合 Kong 失败按最后一名处理）出局者的 `SeatId` 列表。

`match_number` 是服务器只读的局数计数器（当前对局为第几局；MVP 单局固定为 1，多局模式递增）。只用于 UI 展示，客户端不得回传或依赖它做规则判断。

`run.match_limit`：系列赛局数 X（房主开局设定，2-10，默认 5），仅系列赛模式存在（`run` 可选字段）。`players[].eliminated`：出局观战标记（`health==0` 的玩家为 `true`，保留座位、仅公开信息、不可操作）。`result.series`：仅把末（`_series_finished`）存在，形如 `{ finished: Boolean, ranking: [{id, name, wins, currency}] }`（存活者按胜场数降序→同胜场按货币降序，淘汰者不入榜）；非把末不存在该字段。

`run.relics`：系列赛累积持有的遗物（`relic_id → {id, name, desc, min_bid}`），由商店裁决写入；**同种遗物覆写不累积**（重复拍到同 `relic_id` 只替换条目，数量不变）。`run.relic_owners`：遗物持有者（`relic_id → SeatId`），随裁决写入、随护盾消耗清除；遗物效果只对持有者生效（其余玩家无效）。**遗物效果（M4）**：护盾遗物在下一局开局被消耗（随机护盾持有者一格，快照槽位带 `protected` 标记）；Joker 变换遗物使持有者抽到 Joker 时可调 `joker_transform` 变换，未变换 JOKER 在结算/揭示中的分值按 `_relic_card_value` 统一 +2（他人视角同值，非隐藏信息）。

`shop`：仅 `SHOP` 阶段存在——每件 offer 含 `id`/`name`/`price`/`sold_by`（购买者 `SeatId`，`-1` 表示在售），`done` 为已完成（购买或跳过）玩家的 `SeatId` 名单。固定价购买为**公开**信息（无密封字段）。`shop_result`：每次购买**公开**广播（`offer_index → {relic_id, name, winner, amount}`，谁以多少购买），随后开下一局；非 `SHOP` 阶段 `shop` 为空、无新购买时 `shop_result` 为空。

`pending` 是当前行动者待处理的抽牌，`CardView` 之上附带 `source: "draw" | "discard"`，用于客户端区分"可弃掉/可用能力"（仅抽牌堆）与"只可替换"（弃牌堆）。`source` 为公开信息，不泄露牌面。

可见性规则：

1. `pending` 只发送给当前行动者，且仅在 `TURN_DECISION` / `Q_DECISION` 期间存在。
2. `slots[].card` 只在 `GAME_OVER` 时发送给所有玩家；其他时间一律只发送 `HiddenSlot`。
3. `discard` 始终是当前弃牌顶的公开 `CardView`；空弃牌堆发送 `{}`。
4. `slap_rank` 是弃牌顶的公开点数；`slap_open=true` 表示贴牌窗口开启（`TURN_DRAW` 期间，直到当前玩家抽牌）。客户端不得以本地计时决定窗口关闭。
5. `slap_duel` 仅在 `SLAP_DUEL` 阶段存在：`contestants` 为比拼候选人、`duration_ms` 为扫动总时长、`deadline_server_ms` 为扫动截止（服务器时钟）、`target` 为加粗区中心（红心）位置，均为公开信息。客户端不得以本地计时决定比拼结果。
5. `event_log` 不得含有未公开的 `Rank`、`CardId` 或玩家私有查看结果。
6. 客户端收到小于等于本地 `state_revision` 的快照时必须丢弃；对局中止（`match_aborted`）后客户端重置 `last_seen_revision`，以接受新一局从 1 重新计数的快照。

### 4.2.1 身份注册回执 `registered` 与重连恢复 `resume_hand`

```text
// 注册成功后定向发给该玩家本人（不广播）
{
  player_token: String
}
```

`player_token`：服务器注册时生成的随机字符串，唯一标识玩家身份，客户端持久化到本地（`user://identity.cfg`）。断线重连凭它认领原座位。

```text
// 重连成功后定向发给该玩家本人（仅本人）
{
  hand: CardView[],       // 本人当前手牌面（空槽为 {}）
  pending: CardView | {}  // 当前待处理抽牌（若有且属于本人）
}
```

可见性规则：

1. `registered` / `resume_hand` 只发给对应玩家本人，绝不广播。
2. `resume_hand` 只含**本人自己的手牌面**与**自己的待处理牌**；曾偷看过的他人牌面不恢复（符合"记住看过什么"的记忆机制）。

### 4.3 私有查看 `private_reveal`

```text
{
  protocol_version: 1,
  match_id: String,
  reveal_id: String,
  title_key: "INITIAL_PEEK" | "PEEK_OWN" | "PEEK_OTHER" | "Q_PEEK",
  cards: CardView[]
}
```

该消息只发给获得信息的一个 peer。客户端只可短暂显示，不得写入公共状态、回放日志、观战数据或磁盘持久化。V1 不试图阻止玩家手抄或修改自己本地客户端；它保证其他正常客户端不会被服务器泄露暗牌。

### 4.4 命令拒绝 `command_rejected`

```text
{
  protocol_version: 1,
  client_action_id: String,
  code: ErrorCode,
  message_key: String
}
```

错误只发送给请求者，不广播给其他玩家。拒绝时服务器不做任何局部或全局状态修改。

| `ErrorCode` | 含义 |
| --- | --- |
| `PROTOCOL_VERSION_MISMATCH` | 客户端和服务器版本不兼容 |
| `ROOM_FULL` | 大厅人数已满 |
| `ROOM_NOT_OPEN` | 当前不能注册或开局 |
| `NOT_HOST` | 非房主尝试开始 |
| `NOT_ENOUGH_PLAYERS` | 少于两人开始 |
| `MATCH_NOT_ACTIVE` | 对局不在可操作状态 |
| `INVALID_PHASE` | 当前阶段不允许该动作 |
| `NOT_CURRENT_PLAYER` | 非当前行动者尝试回合操作 |
| `INVALID_SLOT` | 槽位不存在或不属于调用者 |
| `INVALID_TARGET` | 目标玩家/目标槽位不合法 |
| `INVALID_SOURCE` | 牌堆来源不可用或不允许 |
| `ABILITY_FORBIDDEN` | 待处理牌不能发动该能力 |
| `DRAW_UNAVAILABLE` | 无可抽牌，且不能通过重洗补充 |
| `INVALID_AMOUNT` | 押注金额不合法（入场 20，+5 递增，上限 100 且 ≤ 当前货币）；`amount==0`（all-in）仅在货币 < 入场时合法；商店购买金额不足（货币 < 该件售价）同样返回 |
| `INVALID_OFFER` | 商店购买的目标遗物不存在或已售出（`offer` 索引越界或已售出） |
| `PROTECTED` | 指定了受防守护盾保护的槽位（他人贴牌 / J·Q 交换目标格） |
| `ALREADY_ATTEMPTED_SLAP` | 已弃用：贴牌不限次数，不再返回该错误（枚举值保留避免位移） |
| `DUPLICATE_OR_EXPIRED_ACTION` | 重复、过期或已被状态推进淘汰的动作 |
| `MATCH_ABORTED_PLAYER_LEFT` | 其他玩家中途断线，本局中止 |
| `HOST_DISCONNECTED` | 房主服务器已经消失 |
| `NOT_DUEL_CONTESTANT` | 不是比拼候选人，不能按 STOP |
| `ALREADY_STOPPED` | 已在比拼中按过 STOP |
| `MATCH_SUSPENDED` | 对局已暂停（有玩家离线），等待重连或房主处理 |
| `INVALID_TOKEN` | 重连凭据无效或座位已被移除 |
| `SPECTATOR` | 出局玩家（`eliminated==true`）尝试操作时返回 |

### 4.5 对局中止 `match_aborted`

```text
{
  protocol_version: 1,
  match_id: String,
  code: "MATCH_ABORTED_PLAYER_LEFT" | "HOST_DISCONNECTED",
  message_key: String
}
```

中止不是结算：不发送 `MatchResult`，不扣生命，不写入历史。客户端应清除对局本地状态并返回大厅/起始页面。

> **断线策略（已实现）**：非当前行动者掉线**不再中止对局**，而是标记 `offline`、加入 `offline_players`；只有当前行动者（或开局记忆阶段任一玩家）离线时 `suspended=true` 暂停。玩家凭注册时获得的 `player_token` 调用 `request_reconnect` 认领原座位：服务器更新其 peer_id、置回在线、定向补发本人手牌面 + 待处理牌并广播最新快照。房主可调用 `request_kick_offline(seat)` 踢出离线者并继续（踢出后剩余人数 < MIN_PLAYERS 时自动中止回大厅）、`request_abort_match` 中止回大厅（销毁房间），或 `request_close_room` 解散房间（广播 `match_aborted` + 关闭服务器连接，全员回初始大厅可重新建房/加入）。

### 4.6 查看高亮 `peek_highlight`

当某玩家执行看牌能力（7/8 看自己、9/10 看别人、Q 查看后决定）时，服务器向**除查看者外**的所有玩家广播被查看牌的位置，用于 UI 显示蓝色光晕标记（约 1 秒）。

```text
{
  player_id: PeerId,
  slot: Slot
}
```

可见性规则：

1. 该消息**只包含位置**（`player_id` + `slot`），**绝不包含 `CardId`、`Rank` 或任何牌面字段**；客户端只用于视觉标记，不写入公共状态。
2. 牌面仍通过 `private_reveal`（4.3）只发送给查看者本人；其他玩家仅看到"有人在查看某张牌"的位置提示，无法得知牌面。
3. 查看者本人不接收 `peek_highlight`（已通过 `private_reveal` 获得完整信息）。

### 4.7 动画事件 `card_exchange_animated`

服务器在状态广播**之前**向所有玩家广播动画事件（客户端先用旧布局定位），`kind` 决定客户端播放的动画：

```text
{
  kind: "replace" | "swap" | "discard" | "slap_penalty" | "slap_resolved" | "slap_gift",
  ...字段见下表
}
```

| `kind` | 字段 | 隐私 |
| --- | --- | --- |
| `replace` | `actor, slot, old_data, big_data` | 旧牌/抽到的牌已是公共信息 |
| `swap` | `a, a_slot, b, b_slot, a_data, b_data` | J/Q 交换的牌面公开 |
| `discard` | `actor, big_data` | 弃掉的牌公开 |
| `slap_penalty` | `peer, slot` | **不含牌面**；罚牌对他人按背面动画，落地后由快照决定显隐 |
| `slap_resolved` | `target, target_slot, card` | 被贴的牌已通过贴牌 reveal 公开 |
| `slap_gift` | `actor, own_slot, target, target_slot` | **不含牌面**（贴牌者自己的牌，他人只看背面） |

贴牌 reveal（`receive_reveal`，标题含"贴牌"）的 `target` 额外携带 `correct: Boolean`，客户端据此对被贴的牌打绿（对）/红（错）炫光；正确贴牌客户端 hold 翻牌至结算（`slap_resolved`），比拼败者由客户端翻回。

## 5. 幂等、顺序与贴牌

1. 客户端每次点击产生唯一 `client_action_id`；同一个 ID 重传时，服务器只能返回首次结果或同一拒绝，绝不能再执行一次。
2. 服务器对每个玩家保留最近 64 个动作 ID，离开房间后清除。
3. 服务器每次接受动作后递增 `state_revision`；所有更改后的快照都带新 revision。
4. 贴牌窗口无固定时长：上一玩家弃牌/用技能后开启（`slap_open=true`）并推进回合；**下一玩家 `take` 时窗口关闭**。正确贴牌进入判定（见第 6 条）；窗口关闭后到达的贴牌请求收到 `DUPLICATE_OR_EXPIRED_ACTION`，不受罚。
5. 同一窗口内玩家可多次尝试；错误贴牌每次罚抽并继续窗口。客户端在判定翻牌期间应忽略新的贴牌点击。
6. 比拼判定：首个正确贴牌开启 **400ms 收集窗**，期间其他正确贴牌加入；结束后仅 1 人则正常解决并关闭窗口，≥2 人进入 `SLAP_DUEL`，各候选人按 `slap_duel_stop`，服务器按**到达时间**映射为扫动位置，最接近 `target`（红心）者获胜并正常解决贴牌，败者无惩罚。未按 STOP 者视为最差距离。
7. 客户端不设贴牌倒计时；窗口关闭由服务器 `slap_open` 状态决定。

## 6. 安全、日志与敏感信息

- LAN MVP 假设玩家彼此可信；它不提供身份认证或端到端加密。
- 服务器权威、私有快照和不透明 `CardId` 用于防止正常客户端“顺手看到”暗牌，不承诺防御能修改自己客户端的恶意玩家或恶意房主。
- 服务器事件日志必须只记录：`match_id`、`state_revision`、请求类型、调用 peer、接受/拒绝码、阶段、耗时。不得在结算前记录真实暗牌。
- 调试日志如确需记录牌面，必须只在本地开发构建启用，并明确不上传、不进入公开崩溃报告。

## 7. V1 对齐验收

协议视为完成前，至少满足：

- [ ] 客户端版本不符无法加入大厅。
- [ ] 所有普通快照都能按 `state_revision` 丢弃旧包。
- [ ] T20 的暗牌泄露检查通过。
- [ ] 每个请求都有对应的接受路径与至少一个拒绝码测试。
- [ ] 连续双击/重传同一动作不会造成双抽、双换或双贴。
- [ ] 中途断线收到明确的 `match_aborted`，没有误结算。

这些条件属于 P0/P1 闸门；在全部完成前，协议版本仍可在 V1 内小修，但必须记录修改日期和兼容影响。
