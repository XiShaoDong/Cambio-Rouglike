# KONG：AI Agent 交接说明（请先读）

本文件用于让后续 Agent 快速理解当前工程，**在不重构既有基础的前提下继续开发**。开始任何改动前，按以下顺序阅读：

1. [KONG_开发文档.md](KONG_开发文档.md)（规则与产品主规格）；
2. [网络协议_V1.md](网络协议_V1.md)（客户端/服务器契约）；
3. [验收与测试计划.md](验收与测试计划.md)（验证和发布闸门）；
4. 本文（工程现状和不可重构边界）。

## 1. 当前基线

- 项目：Godot 4.6，KONG（Cambio + 轻度 Roguelike）LAN MVP。
- 当前目标：先验证 2–4 人的纯基础牌局；Roguelike 内容尚未启用。
- 联网模式：ENet/UDP，房主为规则权威，默认端口 `7007`。
- 当前状态：已搭起可点击的大厅、对局界面、服务器权威状态机和规则模块；**尚未在当前环境运行 Godot 做双实例人工验收**。
- 原因：当前执行环境未发现 `godot` / `godot4` CLI。后续第一优先级是用 Godot 编辑器或安装后的 CLI 按文末清单验证，而不是重写模块。
- 文档状态：MVP 规则 R-01–R-06 已在主规格冻结；字段级协议是 V1 目标契约。现有原型尚未实现协议版本、revision、动作幂等 ID 和完整拒绝码，必须按测试计划逐项补齐并验证。

## 3. 架构不变量（禁止无理由重构）

以下边界已经为 LAN→VPS 迁移预留，后续工作必须保留：

1. `GameState` 保存完整的 `deck`、`discard_pile`、`cards` 和各玩家真实手牌；客户端不保存权威牌面。
2. 客户端只能调用 `request_*` 意图方法（抽牌、选槽位、贴牌等）；服务器收到 RPC 后再次校验调用者、阶段和目标。
3. `GameState._snapshot_for(viewer_id)` 按接收者生成状态。结算前，普通手牌槽位不得包含 `rank`、`suit`、`value`。
4. 查看牌必须走 `receive_reveal` 的定向消息，一次性弹窗展示；不要为“方便 UI”把已知牌写入公共状态。
5. 贴牌胜负以服务器收到的第一条有效请求为准；不要改成客户端倒计时或客户端时间戳裁定。
6. 规则层不能依赖某个 IP、UI 节点或房主画面。未来 Headless VPS 应继续复用 `GameState`。
7. `run_state` 和 `RunModifier` 是扩展缝，不是当前玩法。默认 `enable_relics = false` 必须保持成立。

## 4. 当前状态机与关键约定

`GameState.Phase` 的数值和含义如下。UI 目前以这些数值决定可点击操作；若变更枚举，必须同时更新 UI 和测试。

| 值 | 名称 | 允许的主要动作 |
| ---: | --- | --- |
| 0 | `LOBBY` | 注册、房主开始 |
| 1 | `INITIAL_PEEK` | 每位玩家确认记住开局两张牌 |
| 2 | `TURN_DRAW` | 当前玩家抽牌/取弃牌顶/喊 Kongbaya |
| 3 | `TURN_DECISION` | 替换、弃抽到的牌、发动技能 |
| 4 | `Q_DECISION` | Q 的操作者决定不换或交换 |
| 5 | `SLAP_WINDOW` | 所有人尝试贴任意一张牌 |
| 6 | `SLAP_EXCHANGE` | 成功贴中他人者交出自己的一个槽位 |
| 7 | `GAME_OVER` | 公开所有牌并显示结果 |

关键既定规则：

- 贴牌窗口目前为 2.5 秒；同一玩家一轮贴错后不能再次尝试（R-01）。
- 从弃牌堆拿牌只允许替换；即使牌是 7–Q 也不能发动能力。
- 抽牌堆耗尽时，保留弃牌顶，重洗其余弃牌（R-02）。
- 贴中自己：目标牌弃置，自己手牌数减一。
- 贴中别人：对方的匹配牌弃置，贴牌者选择自己一张牌交给对方，贴牌者手牌数减一。这是已记录的规则歧义取舍，未经设计确认不得改成“直接交换”。
- Kongbaya 只能在行动开始喊；其他人各获得一次完整最终行动；首回合喊且未最低分时只处罚喊话者。
- 完全并列最高者全部扣血；全员完全同分时无人扣血（R-03）。0 张手牌、无法再抽牌、行动计时的确定行为见主规格 R-04–R-06。

## 5. 网络与隐私契约

### 接入

- 房主调用 `Network.host_game`；本机 ENet server 的 peer ID 是 `1`。
- 客户端调用 `Network.join_game`，成功连接后向 `GameState` 注册昵称。
- 所有正常命令最终进入 server 端 `server_*` RPC 和私有 `_server_*` 验证方法。

提交新网络工作前，先检查 [网络协议 V1](网络协议_V1.md)：目标是加入 `protocol_version`、`match_id`、`state_revision`、`client_action_id` 和稳定错误码；它们目前是**缺口清单**，不可假定已经实现。

### 状态消息

| 消息/信号 | 用途 | 是否允许牌面 |
| --- | --- | --- |
| `receive_lobby` / `lobby_updated` | 大厅成员和房主信息 | 否 |
| `receive_state` / `state_updated` | 每位玩家各自的对局快照 | 仅弃牌顶、待处理抽牌（仅行动者）、结算牌 |
| `receive_reveal` / `private_reveal_received` | 一次性查看牌 | 只允许发送给获得查看权的单个玩家 |
| `receive_toast` / `toast_received` | 错误或提示 | 否 |

“客户端可见的卡牌 ID”必须保持为无语义随机令牌。不要改成能按序号反推出花色或点数的 ID。

## 6. UI 已实现的流程

当前 UI 是 code-built prototype，目的是验证操作，不是最终视觉方案：

- 大厅：昵称、IP、端口、创建、加入、成员列表、房主开始。
- 桌面：当前阶段、抽牌堆数量、弃牌顶、所有玩家牌位、公开日志、结算排名。
- 手牌在结算前统一显示为背面。看牌弹窗关闭后再次隐藏。
- J 的操作由 UI 引导为：选对手 → 选自己的牌 → 选对手的牌。
- 贴牌窗口内任何玩家可直接点任意牌位；权威服务器决定对错、罚牌或胜者。

如果未来替换 UI，请先保留这些动作的语义，再调整视觉表现。推荐新建独立 View/Presenter 脚本，逐步迁移，而不是一次性删除 `main.gd`。

## 7. 验证进度记录

已通过自动化验证（E1 环境）：

1. 脚本加载、autoload 顺序正常。
2. 同机双实例 `127.0.0.1:7007` 建房、加入、注册、开始对局正常（`tests/verify_net.tscn`）。
3. 完整回合循环（开局确认 → 抽牌 → 替换 → 贴牌超时 → 下一位）host/client 各 4 回合 PASS。
4. 修复 `_broadcast_state` 广播循环内嵌套推进导致远端漏收阶段快照的问题；并因协议 revision 引入后出现嵌套倒序，本地分发改为 `call_deferred` 保证 revision 单调与发送顺序一致。
5. 协议 V1 四字段（`protocol_version`、`match_id`、`state_revision`、`client_action_id`）与拒绝码全部实现，`tests/verify_protocol.tscn` 23/23 PASS。
6. 断线中止：对局中玩家离开 → 广播 `match_aborted`（MATCH_ABORTED_PLAYER_LEFT）、复位到 LOBBY、房主保留、不计分不扣血；房主断线客户端触发 HOST_DISCONNECTED 并回大厅。端到端双实例验证通过（P0-N08）。

仍待验证：

- 7/8、9/10、J、Q 两种分支、从弃牌堆取技能牌。
- 双实例尽量同时贴牌，确认只有第一个服务端请求成功；贴错罚抽。
- Kongbaya、最终行动、三层同分判定和首回合惩罚。
- 抓包确认结算前未公开手牌没有被常规 snapshot 泄露。

验证发现问题时，优先修复具体的流程缺陷；**不要因为原型 UI 或脚本较长而重写网络或状态机。**

## 8. 推荐的后续任务顺序

1. 完成第 7 节双实例验证并记录结果。
2. 以测试清单 T01–T20 为准，补小型规则测试或手动验收记录。
3. 按网络协议 V1 补齐版本、revision、拒绝码和幂等，然后执行对应 P0-N 用例。
4. 增加基础错误反馈和断线终局提示，严格遵循主规格第 5.6 节。
5. 在基础局稳定后，先做 3 个 feature-flag 控制的单局遗物；每个效果必须先填设计卡。
6. 最后才做 Headless VPS、房间码、认证和断线重连。

> 开发过程中遇到不确定或歧义：先登记到 `docs/问题档案.md`，继续开发明确的部分；若问题影响冻结规则（R-01~R-06）或整体架构，暂停开发等待负责人回复。

## 9. 给后续 Agent 的工作方式

进行任何任务时：

1. 先说明要改哪一个模块、为什么不破坏第 3 节不变量。
2. 改动规则前先更新 `KONG_开发文档.md`，并补对应测试条目；改协议前同时更新 `网络协议_V1.md`。
3. 一次只解决一个可验证问题；保留现有文件名、RPC 名与状态机，除非迁移计划写清楚。
4. 每次提交/交接都说明：改动范围、运行方式、实际验证结果、仍未验证的风险。
5. 若用户只要求文档或设计，**不得顺手重构或补写游戏代码**。
6. 不确定项先入 `docs/问题档案.md`；系统级/冻结规则问题必须暂停等待确认。
7. **用户每次提出 request 后，必须在本轮工作结束时向 `docs/修改日志.md` 追加一条记录**（R-编号递增）：用户请求 → AI 实现 → 用户反馈。无论 request 大小、无论是否完成，都要记录。已完成的工作补充在"当前状态摘要"表中。
