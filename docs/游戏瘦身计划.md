## 1.5 性能基准：重构对服务器资源的意义（2026-11-12）

**测试**：`tests/bench_server.gd/.tscn`（headless，单进程，4 人；5000×4 次快照投影；不建立 ENet 连接）。

| 指标 | 结果 |
| --- | ---: |
| 单次 `HiddenInfo` 快照投影 | **约 41 µs** |
| 4 人一次广播的投影成本 | **约 164 µs** |
| 投影吞吐 | 约 6,100 次广播/秒 |
| 单份快照 JSON | 约 **2.7 KB** |
| 4 人一次广播的 JSON | 约 **10.5 KB** |
| 占 60fps 单帧预算 | **约 0.99%** |

**判读**：服务端是事件驱动（没有每帧重算），按 10 次操作/秒计算，4 人房间约消耗 **0.16% 单核**；4 个房间约 **0.66%**，网络约 420 KB/s。当前规模下服务器资源不是瓶颈。

**结论/打分**：
- 服务器侧性能：**A（无需为性能重构）**。
- 计划中的客户端/教程重构对服务器资源减少的收益 **≈ 0**；它的价值是 UI 一致性、可维护性、教程不再复制规则。
- 如果未来要省服务器资源，应该优化**快照/广播**（增量快照、压缩、减少 `duplicate`），而不是教程组件重构；当前规模不建议做。

> 边界：基准只测服务器投影与快照体积，不含 ENet 序列化/真实网络；即使加上引擎开销，余量仍然很大。

## 2. 阶段 B：客户端重构（教程复用真实组件，服务器零参与）

> 目标：让教程的 Ready/Tab/Shift/贴牌规则与正式对局一致，但**不在本机跑服务器/不发 RPC**。

### B1 抽出表现层宿主

- 从 `scripts/ui/main.gd` 抽出 `PresentationHost`（可命名不同）：持有 `Table3dView`、`board3d`/`hint3d`、`Crosshair`、`ManualPanel`、`CardOrderPanel`、Ready/条件按钮、HUD、CardTooltip。
- 定义 `SnapshotSource` 接口：只暴露 `state_updated/lobby_updated` 等只读快照信号；可选 `request_*`（网络或本地）。
- `main.gd` 保留为组合根：网络源 → 宿主；教程源 → 同一宿主。

### B2 本地会话

- 教程使用**进程内** `GameState`/`SlapSystem` 实例（或一个 `LocalGameSession` 适配器），不创建 `ENetMultiplayerPeer`、不 `rpc_id`、不占端口。
- A岚的操作由本地脚本在固定延迟调用本地 `request_*`；规则仍由真实 `GameState/SlapSystem` 判定，不做手写状态机。
- 服务器资源消耗为零；只增加客户端少量 CPU。

### B3 教程接入真实 UI

- Ready：复用正式对局的 Ready 按钮/提示板位置与交互，不再自绘 `TutorialOverlay` 的 Ready。
- Tab：复用 `ManualPanel` + `board3d` 的挂载方式与位置。
- Shift：复用 `CardOrderPanel` 的位置/开关。
- 牌桌/大牌/翻牌/罚牌：全部走 `Table3dView`/`CardFly`/`CardBlock` 的真实路径；教程只负责喂快照和旁白。
- 教程层只保留 `TutorialDirector`（步骤、文案、说话、锁定/解锁输入）和 `TutorialSteps`（脚本化输入/固定牌序）。

### B4 贴牌真实规则

- 删除教程里脚本化的「阿岚贴牌/重置比赛」；改为本地会话的真实贴牌请求 + 真实 `SlapSystem`（窗口/对错/罚牌/比拼/交牌）。
- 教学仍可用固定随机种子/固定牌序，但不绕过规则判定。

### B5 验证与风险

- 单测：本地会话状态流、贴牌窗口、交牌、结算；现有 `verify_tutorial` 改为宿主集成测试。
- 在线回归：`verify_protocol`、`verify_swap`、`verify_duel`、`verify_reconnect`、`verify_net` 必须不受影响。
- 风险：`main.gd` 耦合面最大（约 2.8k 行）、鼠标捕获/看板拾取/输入分发；建议先抽接口、保持在线路径行为不变，再迁教程。
- 量级：中等客户端重构，不是几天的小改；服务器/规则/协议零改动。
